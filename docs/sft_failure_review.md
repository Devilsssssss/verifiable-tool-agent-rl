# SFT 开发失败复盘与下一轮设计

日期：2026-10-12。此文档记录开发诊断，不是正向研究结论。

## 已完成的排查

- v4 修复 Arrow 参数合并与训练/推理工具 schema 排序差异，600 视图审计通过。
- v5 变换训练邮箱、商品名称和问法，仍为 300 个独立任务 / 600 视图。
- v6 补充 300 个首调用视图，覆盖 12 种训练句式。
- v7 改用四种 `For account + 邮箱` 首调用句式，视图总数仍为 900。
- v8 在全部训练视图中混合数字/哈希邮箱结构与四个域名，视图总数仍为 900。

掩码、schema、生成前缀和无截断检查通过，只证明这些处理与实现一致，
不能证明模型有业务能力。低 teacher-forced loss 不等于自由生成成功。

## 两类相互作用不能混为一谈

v7 首调用探针固定前五个开发验证任务，覆盖五个业务族。v8 使用同一探针。
只检查第一个 `lookup_user` 的参数，所有 35 个调用都不执行完整业务任务。

| 条件 | v7 正确首调用 | v8 正确首调用 |
| --- | ---: | ---: |
| 原验证问法 + 验证邮箱 | 0/5 | 0/5 |
| 原验证问法 + 一个同族训练邮箱 | 5/5 | 5/5 |
| 首调用训练问法 + 验证邮箱 | 0/5 | 0/5 |
| 原始首调用训练样本 | 5/5 | 5/5 |
| 完整轨迹训练问法 0 + 验证邮箱 | 5/5 | 5/5 |
| 完整轨迹训练问法 1 + 验证邮箱 | 5/5 | 5/5 |
| 完整轨迹训练问法 2 + 验证邮箱 | 5/5 | 5/5 |

替换邮箱时保留原请求，其余条件会改变商品表述，故不构成完全交叉的因果实验。
结果支持问法与邮箱拼写发生交互，而非所有未见邮箱都无法提取。
v8 的随机结构增强没有解决该诊断中的失败；不能据此断言数据增强普遍无效。

## 下一轮应先重做覆盖设计

1. 只使用训练实体，让每一种请求框架都出现每一种邮箱拼写结构，
   避免当前“一个任务随机分到一种框架/一种邮箱”造成稀疏交叉覆盖。
2. 同时生成首调用和完整正常轨迹，框架选择不与业务族、邮箱域名或位置绑定。
   用脚本统计交叉单元的样本数，并逐条重放专家与错误恢复轨迹。
3. 先固定训练任务内的诊断子集，只替换邮箱的字符结构；保持商品、问法和
   业务状态不变。使用完整交叉矩阵测首调用，避免再次只看总体均值。
4. 比较学习率较低的 SFT 与当前设置，明确新增视图改变了预算；另作等更新步
   控制，避免将“训练更久”的差别归因于某一种增强方式。
5. 仅在完整 validation-60 严格成功率至少 50%、五个族均有成功时进入 RL。
   失败不使用冻结确认集选版本，也不通过改解析器或奖励规则掩盖错误。

这是下一阶段的设计，尚未实现或训练，不能写成已完成的简历成果。

## RL 结果的实际边界

旧两组 30 步 GRPO 原生日志中，稀疏奖励仅 1 步、过程奖励仅 2 步有非恒定组。
常量组的奖励优势为零；KL 项仍可能产生梯度。训练奖励高不能证明模型改善。
下一轮必须保留原生组内标准差、零方差比例、截断比例和工具失败频率，
并与固定的完整验证集相连。推理预检不能代替这些原生日志。
