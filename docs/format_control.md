# 输入格式修复对照

2026-10-12。在查看 v4 的行为结果前固定以下口径。

## 已确认的处理缺陷

v3 的嵌套参数对象被 Arrow 合并成共享结构，增加了无关的 `null` 参数。
另外，训练序列化工具 schema 时排序键，推理直接传 callable，键顺序不一致。
这两个缺陷与性能下降之间的因果关系尚未建立。

`canonical-v4` 将参数保存为稳定的 JSON 字符串，Qwen 模板直接输出参数对象；
训练与推理共用同一转换，并使用同一排序后的工具 schema。
转换保留所有原有参数（包括错误的非空参数），不代替模型纠正调用。
业务状态、严格成功标准、奖励、数据划分、用户提示均不变。

## 对照与门槛

1. 用 canonical-v4 推理格式重新评测 v3 的 validation-20，观察仅更换输入格式的效果。
2. v4 从同一原始模型重新训练：300 正常视图 + 300 修复视图，1 epoch，
   学习率 2e-4，batch 1，梯度累计 8，seed 45，LoRA r16 / alpha32。
   与 v3 的样本数、训练轮数、超参数保持一致；序列长度和监督 token 数会改变。
3. v4 先检查 validation-20；全部任务调用预算保持原样，每轮最多生成 512 token，
   temperature 0，seed 42。之后检查完整 validation-60。
4. 只有完整验证集严格成功率至少 50%，且五个任务族都有成功任务，才用该模型开展 RL。
   该门槛是本项目的实验决策，不是行业标准。

如果验证失败，先逐条分析调用和数据覆盖，再调整训练数据；不把测试集用于选择检查点。
既有 test-120 已参与开发诊断，不能继续称为未触碰的最终评测集。
最终 RL 结论需要固定新评测集、相同 SFT 初始化与采样预算，并如实报告多个种子。

## 验证驱动的下一轮

v5 使用训练实体/措辞增强，仍在 validation-20 严格成功 0/20。
固定 10 个验证任务的邮箱与商品，只替换用户问法的首调用探针中，
原始措辞为 0/10，三组已见训练措辞分别为 10/10。
这支持存在措辞敏感性；探针不测业务任务成功，也不证明全部失败只有此原因。

v6 在 v5 的 300 正常 + 300 修复视图上增加 300 条首调用监督，
使用 12 种训练用邮箱句式，实体均来自训练任务，不复制验证或确认集原句。
仍从原始模型训练 1 epoch、seed 45，其余超参数不变。
总视图数变为 900，独立业务任务仍是 300；训练预算和监督构成均改变，
因此不能把 v5/v6 差值解释成等预算的单变量因果效果。
进入 RL 的完整验证集门槛保持不变；失败后不使用新确认集挑选版本。

v6 前几条验证轨迹仍复制了 `For account`。下一轮 v7 将新增的 300 条首调用
视图改成四种 `For account + 邮箱` 句式，其他 600 条正常/修复视图保持不变。
这明确共享了验证问法的通用前缀，是验证驱动的定向补充；验证集已不能证明
未见措辞泛化。仍不使用验证实体、业务状态或完整原句做训练。
v7 从原始模型训练 1 epoch / 900 视图 / seed 45，RL 门槛与独立确认集不变。

v7 验证仍失败后，5 条首调用控制显示：原问法 + 训练邮箱为 5/5，
首调用训练问法 + 验证邮箱为 0/5。完整问法探针的其他已见训练问法为 5/5。
该交互支持同时检查邮箱拼写结构，不证明所有任务失败只有一个原因。
v8 在 300 个训练任务中混合短数字、长数字及哈希邮箱，包含 `example.test`
和三种训练域名，不使用验证/测试邮箱或保留前缀。正常、修复、首调用视图
均使用替换后的邮箱，共 900 视图；首调用仍采用 v7 四种问法。
从原始模型训练 1 epoch / seed 45，其他超参数不变。完整验证集的 RL 门槛不变。
域名与问法的选择来自开发诊断；后续验证结果不能作为完全未见分布的证据。

实际结果：v7/v8 各完成 validation-20，严格成功均为 0/20，错误邮箱均为 20/20；
逐条重放通过，原分数未变化。v8 的交叉首调用探针未改善上述结果。
两版均未通过原始提示协议的初筛，未启动新 GRPO；之后的显式字段协议对照另行
完成了 validation-60 和冻结确认集评测，不能回写为原始提示协议的成绩。
下一阶段的数据设计见 [失败复盘](sft_failure_review.md) 和
[v9有界方案与结果](factorial_v9_protocol.md)。1000视图掩码审计通过，但两个学习率
候选的原提示validation-20均为0/20，未过门槛，已停止同类SFT扩充。
v8显式邮箱字段诊断改变了输入协议；在该协议内，基座/v8的validation-60为0/60
与60/60，冻结确认集为2/120与120/120。它不能算作原协议SFT/RL增益，也不能
替代原协议的完整validation-60门槛。

## 后续 RL 预检

通过完整 validation-60 后，先在前 10 条增强训练任务上每题采样 4 条轨迹，
temperature 1.2、top_p 0.98、seed 101，每轮最多 512 token，原任务预算不变。
同时记录 sparse/shaped 的组内奖励差异。这是独立推理预检，不能冒充原生
GRPO 的采样日志。如果对应奖励模式的 10 组全都恒定，暂停该模式训练。

若有非恒定组，先执行 10 步 GRPO 试验：相同 SFT adapter、300 条增强训练任务、
num_generations 4、generation_batch_size 4、梯度累计 4、学习率 1e-5、
completion 总长度 1536、最多 8 次工具循环、beta 0.02、上述采样参数。
只用 validation-60 看试验结果，不据此宣布 RL 有效。原生日志的组内标准差、
截断比例和工具失败率必须随结果一起保留；下一阶段才扩预算与训练种子。
