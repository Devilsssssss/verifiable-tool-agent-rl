# 输入格式修复对照

2026-10-12。在查看 v4 的行为结果前固定以下口径。

## 已确认的处理缺陷

v3 的嵌套参数对象被 Arrow 合并成共享结构，增加了无关的 `null` 参数。
另外，训练序列化工具 schema 时排序键，推理直接传 callable，键顺序不一致。
这两个缺陷与性能下降之间的因果关系尚未建立。

`canonical-v4` 将参数保存为稳定的 JSON 字符串，Qwen 模板直接输出参数对象；
训练与推理共用同一转换，并使用同一排序后的工具 schema。
转换保留所有原有参数（包括错误的非空参数），不代替模型纠正调用。
业务状态、严格成功标准、奖励、数据划分、用户提示均不变。

## 对照与门槛

1. 用 canonical-v4 推理格式重新评测 v3 的 validation-20，观察仅更换输入格式的效果。
2. v4 从同一原始模型重新训练：300 正常视图 + 300 修复视图，1 epoch，
   学习率 2e-4，batch 1，梯度累计 8，seed 45，LoRA r16 / alpha32。
   与 v3 的样本数、训练轮数、超参数保持一致；序列长度和监督 token 数会改变。
3. v4 先检查 validation-20；全部任务调用预算保持原样，每轮最多生成 512 token，
   temperature 0，seed 42。之后检查完整 validation-60。
4. 只有完整验证集严格成功率至少 50%，且五个任务族都有成功任务，才用该模型开展 RL。
   该门槛是本项目的实验决策，不是行业标准。

如果验证失败，先逐条分析调用和数据覆盖，再调整训练数据；不把测试集用于选择检查点。
既有 test-120 已参与开发诊断，不能继续称为未触碰的最终评测集。
最终 RL 结论需要固定新评测集、相同 SFT 初始化与采样预算，并如实报告多个种子。

## 验证驱动的下一轮

v5 使用训练实体/措辞增强，仍在 validation-20 严格成功 0/20。
固定 10 个验证任务的邮箱与商品，只替换用户问法的首调用探针中，
原始措辞为 0/10，三组已见训练措辞分别为 10/10。
这支持存在措辞敏感性；探针不测业务任务成功，也不证明全部失败只有此原因。

v6 在 v5 的 300 正常 + 300 修复视图上增加 300 条首调用监督，
使用 12 种训练用邮箱句式，实体均来自训练任务，不复制验证或确认集原句。
仍从原始模型训练 1 epoch、seed 45，其余超参数不变。
总视图数变为 900，独立业务任务仍是 300；训练预算和监督构成均改变，
因此不能把 v5/v6 差值解释成等预算的单变量因果效果。
进入 RL 的完整验证集门槛保持不变；失败后不使用新确认集挑选版本。
